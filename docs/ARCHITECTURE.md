# Architecture

One Rust binary, UI in iced (tiny-skia CPU renderer). It runs as a resident tray
app: the overlay window is created hidden at start, so a trigger only has to
capture the screen and show it.

## Layout (0.1.8: by feature)

The code is organised by FEATURE (what the user sees), plus one shared layer and the app shell:

```
src/
  main.rs            start, CLI (frozen contract), single instance, Trigger
  app/               the iced app shell: App state, Message, update / view dispatch, opening and closing,
                     keys, every monitor (monitors.rs), the normal windows and pins (windows.rs), the
                     update experience (updates.rs), the daemon's start (shell.rs); screens/ = the shell's
                     own screens (toast, tray menu, update card / pill, the Windows setup's window)
  features/
    circle/          Circle to Search: actions/ (the action registry: crop, copy, save, search in browser,
                     QR, share, entities), screens/ (overlay canvas, bar, screen edge), app/ (selection,
                     bar, zoom, actions, quick actions)
    text_reading/    the readers (PP-OCR helper, Windows OCR, models), Copy text, app/ (reading state,
                     word picking), screens/ (model download card)
    translate/       one-shot translate (pipeline, erase, draw, glossary, the language table), mt/ (offline
                     models), action.rs, screens/ (the translate pill, the language picker)
    live_translate/  the click-through layer (platform side), live.rs (frame logic), screens/ (layer, controller)
    ask_ai/          providers and clients, the browser provider, ask.rs (the action), chats.rs (history),
                     app/ (the chat's handlers), screens/ (the chat, the model list)
    snip/            the editor (annotate/), capture/ (snip frames, long capture, pins' capture), action.rs,
                     snip_more.rs, app/ (Snip, More, toolbar, screen tools), screens/ (the flow, toolbar,
                     Steps strip, long capture and its pop-up, screen tools)
    song/            song search, its history, screens/
    settings/        the Settings window and its pages, previews, the Labs switches (labs.rs)
    onboarding/      the first-run steps
  shared/            what every feature uses and no feature owns
    kit/  theme.rs  touch.rs        the one UI kit and its tokens; the config-to-kit glue; touch as mouse
    platform/        the OS: capture core, hotkey/, sys/, autostart, and the windows / monitor / shape / tray glue
    config/  app_language/  store/  update/  setup/  history/  log.rs  paths.rs  secrets.rs  net.rs  diagnostics.rs
```

A feature folder holds its logic at its root, its part of the shared `App` in `app/` (`impl App` blocks:
Rust allows them in any module, so `app/` keeps only the dispatch), and its views in `screens/`.
`onboarding/` and `settings/` are all UI.

Rules (source scans in `app/arch_tests.rs`, each proved to fail on a planted violation):
1. `shared/` never imports `features/` or `app/` (`shared_never_imports_features_or_app`).
2. A feature uses another feature only through that feature's `mod.rs` (`features_meet_only_through_mod_rs`).
3. Screens never style; only the kit styles; the kit depends only on itself; the OS glue imports no UI; the
   backend (every non-UI file) imports no UI; windows are shown only by `platform::windows::show`, resized only
   by `platform::monitor::resize`; every text names a bundled face; one scrollbar, one dropdown; every kit press
   is a focus stop. Words only from the string table (`shared/app_language/tests.rs`).
Rules 1 and 2 carry a ratchet (`SHARED_LEGACY`, `FEATURE_LEGACY`): the files that still break them when the
folders were made. The lists only shrink: a file that is clean must leave its list.

**Add a feature** = one folder + one registry entry:
1. `src/features/<name>/mod.rs` (its public face: what other features and the shell may use), its logic beside
   it, `app/` for its `impl App` handlers, `screens/` for its views (kit parts only).
2. `pub(crate) mod <name>;` in `src/features/mod.rs`.
3. One entry in the list that shows it: an action in `features/circle/actions/mod.rs` (`ACTIONS`), a Settings
   page in `features/settings/pages/mod.rs` (`PAGES`), a Labs switch in `features/settings/labs.rs`, a tray row
   in `shared/platform/tray.rs` (`entries`), a quick action in `shared/config` (`QuickAction`).
4. Its messages in `app/message.rs`, dispatched in `app/update.rs` to the feature's `app/` handlers.
5. Its words in `shared/app_language/strings.rs`; its UI files are covered by the word scan
   (`UI_SOURCES` there) and the arch tests (`in_ui` there: `features/*/screens`, `features/*/app`).

## Data flow

1. **Trigger**: shortcut, tray or `opencircle capture` sends `Trigger::Capture` or `Trigger::Quick` into one channel.
2. **Capture**: `capture::mouse_first()` (snip: `every_monitor()`) returns a `Frame` (RGBA, size, origin, scale).
   It runs on its own thread (a Wayland portal can wait minutes for the user's OK);
   `Message::Captured` then shows the pre-created window.
3. **Overlay**: the RGBA bytes become the `image::Handle` drawn full-screen. The same
   bytes are later cropped by actions (shared, never copied whole).
4. **Selection**: the canvas reports press/move/release (screen px; the App maps them
   to image px through `overlay::View`); on release `overlay::settle` decides: a zig-zag
   (3+ sharp corners) = a scribble (the box of its padded convex hull, which is also the
   clear area), a mostly straight drag = the rectangle it spans, anything else = the
   loop's bounding box, a tap = the word there (`features/text_reading/app/word.rs`). A new press starts over
   (redraw); a press on a corner handle resizes, on highlighted words a drag stretches
   them across lines (Shift+click too), elsewhere inside moves; Shift adds a selection (Ask AI / Text get every
   crop stacked in one image, the rest the box around all). The ask bar at the bottom
   opens Ask AI with its text (in "wait" mode, Enter with nothing typed = Search). Its
   buttons: Include screen, Copy, Save, Translate, Live, Music, Edit (no Search / Ask AI
   / Text buttons; their keys L / A / T stay). Text selection needs the screen's text.
   Who reads it is `ocr::route` (`App::system_text`, decided per opening in `App::text_by`):
   on Windows, Windows OCR (`ocr::system`) reads the whole screen from the capture on
   (`App::open` -> `read_more` -> `read_band` of the whole screen, a below-normal thread),
   first as it is (selectable ~0.14 s after the first frame), then under 150 % doubled,
   which replaces it (`system::passes`); a failed read (no recognizer, an RTL language)
   falls back to the helper for that opening. The engine is freed after 60 s unused. Otherwise (Linux, `pp_ocr`, Arabic) the helper reads on demand, never at
   open (#123; `word::Screen`, `App::read_more`): nothing is
   read while the opening animation runs; after it the held helper starts (`App::warm`).
   A press, tap, Shift+click or Ctrl+A reads the full-width band under it first (at
   once, `ocr::recognize_band` with only the band's new rows); once text was used (off
   Windows: once the helper is warm, `Message::Warmed`, so the I-beam shows over text
   before any press), the rest follows band by band, nearest the pointer first, gently (the helper on at most
   two cores, below normal priority: `features/text_reading/worker.rs` `Gentle`). One band at a time. A
   drag that began on text before its band arrived becomes a text selection then; one
   let go before it is held (with the keys after it, e.g. Ctrl+C) until it arrives
   (`App::held`). Without the OCR models a note over the bar (`App::reader_note`, state
   `Reader`) offers their download, one click.
5. **Action**: a bar button, Enter (the first action) or the action's key sends
   `Message::Run(&Action)`. `App::run` crops the selection in physical pixels, then:
   `Run::Finish(f)` closes the overlay (so dialogs aren't under it) and calls `f(crop)`
   on a thread (`App::confirm_after`: encoding, clipboard, file; its pill comes back as
   `Message::Confirm`). Clipboard writes and link launches never run on the UI thread;
   `Run::AskAi` opens the AI chat over the frozen frame (the bar hides,
   the selection stays). Slow work (PNG, browser launch, keyring, HTTP stream, model
   download, OCR) runs on a thread via `background`; results come back as
   `Message::AiChat(id, ai_chat::Msg)` and stale ids are ignored. Dropping a panel
   aborts its task, which disconnects the thread (an AI stream then stops).
6. **Close**: Esc (any focus) or a finishing action: `close()` takes the whole per-capture
   state (`app/opening.rs`: add new per-capture fields THERE, never to `App`): the panel and the
   frame go; the window shrinks, then hides (`Hiding`). `App::o` is `None` while closed
   (`opening::Open`); `update` drops every message that needs an opening then (`update::works_closed`:
   a new message that must work with no overlay open goes in that list). A press outside the
   panel starts a new selection and drops the panel.

## Change recipes

**Hide or show an unfinished feature (Labs):** `src/features/settings/labs.rs` is the one place: a `Feature`, its `[labs]` switch
(`Labs`, parsed in `shared/config/parse.rs`, all off by default), and the data the rest reads: `action_feature` (which action id
belongs to it: shortcuts in `hotkey::plan`, `opencircle run`, `actions::for_key`), `bar()` (the bottom bar's buttons),
`tray::entries`, `settings::pages::PAGES` (`lab`) / `slots`. Never an `if` on a feature elsewhere: add it to that data. A hidden
feature keeps its settings in the file. A feature that ships leaves Labs (Snip, 0.1.3): its `Feature` goes, its `[labs]`
key stays in `Labs`, read and written unchanged (an older OpenCircle reads it) and used for nothing. Schema changes: bump `config::VERSION`; a step that changes a value goes in
`Config::parse` (it knows the file's version, e.g. schema 3 sets `selection.after` to "wait"),
and `config::migrate` copies the old file to `config.toml.bak-v<old>` and rewrites it.

**Keep a new kind of record** (a search index...): a file in `src/shared/store/` with its functions
(blocking: call them on a thread), and ONE new entry at the END of `store::MIGRATIONS` (its tables; never
edit a shipped entry). Never put image bytes or secrets in it; tests point `store::test_path` at a temp file.

**Add an action** that finishes at once (like Copy):
1. Create `src/features/circle/actions/<name>.rs` with `pub const ACTION: Action = Action { id, label,
   tip, key, icon, run: Run::Finish(run) }` and its `fn run(crop: Crop) -> Result<(), String>`
   (copy `copy.rs`; keep blocking work off the UI thread, see `save.rs`). Keys:
   DESIGN.md "Shortcuts".
2. Add `mod <name>;` and `<name>::ACTION` to `ACTIONS` in `features/circle/actions/mod.rs`, in
   action-bar order. The first entry is the Enter default.
3. Icon: the subset font has search, sparkles, type, languages, pencil, copy,
   download, arrow-up, square, x (codes in `assets/lucide/subset.sh`). For another
   glyph, add its code to `subset.sh`, run it, commit the `.ttf`.
4. `cargo test`: the registry tests check ids, labels, tips and keys are unique and
   that the icon is in the font.

**Add a quick action** (its own shortcut, not a selection action): a `QuickId` variant (its name is the file's), its Labs feature in `labs::action_feature`, its Settings name and hint (`settings::state::action_name` / `quick_hint`), and its unbound entry in `Config::add_new_quick_actions` (the default file stays byte for byte; Settings shows the row, the file gets it at the next save; `opencircle run <id>` needs no entry).

**Add an action that stays on screen** (a card like the AI chat):
1. As above, with its own `Run::<Kind>` variant (like `Run::AskAi`).
   The action file holds the work (blocking functions, pure logic + its tests).
2. In `features/ask_ai/screens/ai_chat/` (or a screen of its own): a `State` variant, its start in `AiChat::open` (slow work via
   `background`, keep the abort handle in `work` if it should stop with the panel),
   its `Msg`s in `AiChat::update`, its body in `view.rs` (kit parts only). Messages the App must act on
   (close, open another panel) are matched first in `App::on_ai_chat`.

**Add a shared widget**: screens never set a style themselves; they take
their controls from the kit (`shared/kit/`: one file per
control, styled only from `kit::tokens` / `kit::themes`, no config or clock, motion as an
`f32` progress). A new kit

(the key names the screen and the thing: `g_lang_desc`), then `t!(key)` (or `tr(S::key)`) where it is shown; a value
in a sentence is `{}` and goes through `app_language::fmt(S::key, &[&value])` (in Arabic a Latin value is isolated,
U+2068/U+2069), a count through `app_language::count(n, [one, two, few, many])` (Arabic's plural forms). Never a
literal: `app_language::tests` fails on a key without both languages, a key no code uses, and any word left in a
Settings or onboarding file (`NOT_UI` lists the literals that are not words: key names, ids, the CLI). The kit takes
its few words as parameters (`hero::Words`, `shortcut_field`'s "Not set"): it never reads the table.

**Add a language**: a `Lang` variant (+ `code`, `rtl`, its `lang_<code>` name key for `endonym`), a column in the
table's macro (`[en, ar, …]`) and its text in every entry, a `Choice` in `CHOICES` (Settings' App language list). The
language resolves from `general.app_language` (Settings; "" = follow), else `general.language` (onboarding's pick), else
the OS's (`app_language::of_config`); `apply` sets it on the UI thread (Settings' state at open and on a pick,
onboarding's language step): the next redraw of every window speaks it, no restart.

**Make a screen direction-aware**: its view starts with `let _dir = kit::dir::scope(app_language::rtl());` (the kit
reads the direction while the view builds; views that don't set it stay left to right), writes its side-by-side
children in reading order with `dir_row![a, b]` / `kit::dir::row(vec)` (never `row!` with a `.push` after it: the push
lands at the wrong end in Arabic), aligns text columns with `.align_x(kit::dir::start())`, pads one side with
`kit::dir::pad`, and uses `Icon::directed()` for arrows. The kit parts do the rest (setting rows, sidebar, header with
the caption buttons top left, segmented/Off-On order, slider and progress from the right, dropdowns, cards, hero).
Never mirrored: key caps, numbers, paths, URLs, the logo, colour strips, preview stages. A wrapped right-to-left
paragraph goes in a column (a `sub` straight in a container was laid out past its edge). Older screens with their own
`rtl: bool` (Snip toolbar, Steps strip, ruler, long-capture hint, `option_list::foot` / `ActionRow`) take
`kit::dir::rtl()` when they move onto the table (part 2b); the language picker, `option_list::{opener, choice, group}`
and `field::search` already do. A floating window (toast, update pill / card, tray menu: `ui::windows`) is built and
its size measured inside `windows::spoken(..)`; the translate session's `view` sets the direction itself. Backend code
never writes a sentence the user reads: it returns a typed value (`update::Answer`, `hotkey::Reserved`,
`config::ShortcutFault`, `ai::models::Tag`, the settings `Why`, `ocr::OcrError`) whose `Display` stays English for logs
and tests, and the UI maps it to table keys (`general::answer_words`, `model_download::why`, `model_list::ai_words`).
A pill text a backend names is `Said(S::key)` (`actions::copy::COPIED_PILL`). The release notes are the release's own
English text: the What's new card keeps them as one left-to-right block (`update_card::quoted`).

**Add a colour**: a theme colour goes in every theme of `kit/themes.rs`; one
that is the same in every theme in `kit::tokens::fixed`. Nowhere else.

**Add an active look** (a preset): a `LookTheme` variant and its row in
`config::PRESETS` (a new colour set: a `ColourSet` variant and its colours in
`theme::colours`), then its tile in `features/settings/state.rs` `LOOKS`. The tests check
every preset round-trips and draws no key colour on the live layer.

## Test hooks (not for users)

Read them through `sys::test_hook`: a release build (what the VM builds and users run) reads a hook only
with `OPENCIRCLE_TEST_HOOKS=1` set too; debug and test builds always do. `OPENCIRCLE_TEST_UPDATE_URL` stays
outside it (the update gate runs published builds).

- `OPENCIRCLE_TEST_FRAME=<8-bit RGBA PNG>`: capture returns this image instead of the screen.
- `OPENCIRCLE_TEST_LANGUAGE=<tag>` (e.g. `ar`): the OS's language as `sys::locale::language` reports it: the setup
  window and a fresh onboarding speak it (VM runs in Arabic without changing Windows' display language).
- With the editor open, its Esc (Back) takes the test shot (`OPENCIRCLE_TEST_SHOT`).
- `OPENCIRCLE_TEST_LIVE_SHOT=<out.png>`: live translate saves its layer once the first patches (or the first error) are drawn.
- `OPENCIRCLE_TEST_UPDATE_URL=<release JSON URL>`: the update check asks this URL (http allowed: a local fake
  release server) 3 s after start, also from a 0.0.0 build. Downloads still need a signature by `RELEASE_PUBLIC_KEY`,
  or, only with this hook, by a throwaway key baked in at BUILD time (`OPENCIRCLE_TEST_RELEASE_KEY`; release.yml never
  sets it). `scripts/update-gate.ps1` drives it as the release gate (docs/RELEASING.md step 9).
- `OPENCIRCLE_TEST_CAPTURABLE=1`: our floating windows (Steps strip, pins, pills, the pinned chat's, tray menu;
  the update's pills and card always show) are not excluded from screen capture on Windows (VM screenshots of them over the desktop; they then
  also show in the next capture's frozen frame). Linux takes them out of each grab but Snip's (`Windows::leave_frame`) whatever this says.
  Snip's grab always has them in, as targets (`window_rect::widgets_in_grab`; owner, 2026-11-10).
- `OPENCIRCLE_TEST_SHOT=<out.png>`: Esc saves what the overlay shows before closing
  (shot ~150 ms after Esc, with no message in between: a relayout would drop the
  text editor's drawn text from the shot).
